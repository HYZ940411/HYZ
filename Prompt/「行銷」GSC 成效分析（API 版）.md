# GSC 成效分析（API 版）

## 第一步：先確認目的，不要先抓資料

**在跑任何 API 之前，先問使用者這次分析要幹嘛。** 不要因為「反正資料抓下來都有」就
全部抓一遍再想要講什麼 —— 那會產出一份什麼都提到、但什麼都不深的報告。目的決定
要抓哪些維度、比哪兩期、KPI 是什麼、報告長什麼樣。

用選項式提問，一次問完。至少要確認：

1. **這次的目的是哪一種（可複選）** —— 見下方五種
2. **站台**（先跑 `--list` 把可用站台列出來給使用者選，不要讓他手打）
3. **期間**，以及要不要對比前期
4. **重點頁面清單** —— 我方供稿／正在合作的那批文章網址。沒有的話問有沒有，
   真的沒有再退回「依點擊取前 10–12 名」，並在報告裡寫明這是預設排序
5. **文章發布日期** —— 只要重點頁面裡有任何一篇是期間中才上線的，就必須拿到

## 五種目的，各自要什麼

| 目的 | KPI | 要抓的維度 | 報告長相 |
|---|---|---|---|
| **1. 對客戶交代成效**（續約／請款） | 我方頁面的點擊、曝光、排名逐期變化 | `date`、`page`，兩期 | 成長百分比放最前面，「之前 → 之後」放底下；我方頁面與其他頁面分開列 |
| **2. 策略驗證**（假設對不對） | 目標大字的排名軌跡、字族的曝光廣度 | `page`+`query`、`query`，兩期 | 圍繞字族：現在排到第幾名、跟上期比前進多少、卡點在排名還是點擊 |
| **3. 找可執行的優化清單** | 預估可回收點擊數 | `page`、`query`、`page`+`query`，單期即可 | 依「動手就能回收的量」排序的清單，每條附現況數字與預估效益 |
| **4. 診斷異常**（流量掉了） | 掉最多的頁面與字 | `date`、`page`、`query`，兩期逐頁相減 | 先給結論（掉在哪、掉多少），再給排除法：索引狀態、改版、演算法更新 |
| **5. 選題與需求探勘** | 有曝光但我們沒有對應內容的字 | `query` 抓滿（API 上限 25,000 列） | 依曝光排序的字群清單，標出目前由哪個頁面承接、或根本沒人承接 |

目的 1、2、4 需要兩期資料；3、5 單期就能做。**若使用者要的是 1 或 2，但期間資料
不足（例如站台剛建立、或 16 個月保留期外），要先講清楚做不了哪一段，再問要不要
改做 3。不要硬湊一份看起來像成長報告的東西。**

## 第二步：抓資料

```bash
python3 tools/gsc_fetch.py --list                       # 先確認站台字串
python3 tools/gsc_fetch.py --site <站台> \
    --start YYYY-MM-DD --end YYYY-MM-DD \
    --out "<客戶資料夾>/API_<起>_<迄>" [--prev] [--daily-query]
```

- 目的 1／2／4 → 加 `--prev`（自動抓等長的前一期）
- 目的 2 要看關鍵字逐日趨勢 → 加 `--daily-query`（列數很大，只在需要時抓）
- 憑證未設定會提示跑 `tools/gsc_auth.py`；設定步驟見 `tools/README.md`

**抓完先看腳本印出的涵蓋率**（查詢層級點擊 ÷ 圖表檔點擊）。GSC 會隱去過於稀有的
查詢，API 也拿不到，所以查詢層級永遠小於總數。這個數字要寫進報告的資料限制。

API 相對介面匯出的三個關鍵優勢，直接影響能做到什麼：

- **`page`+`query` 一次拿到對應關係** —— 不必再說「這是依主題推估」。每篇文章實際
  排上哪些字是可以直接回答的事實。
- **查詢不再被截在 1,000 列** —— 介面匯出常常只涵蓋一半的點擊，API 分頁抓得完。
- **查詢可以加 `date` 維度** —— 關鍵字的成長與變化才做得出來。

## 第三步：計算

用 Python（pandas 或標準庫 `csv` 都可以）算完後**輸出成一份 JSON**，MD 與 HTML 都
從這份 JSON 產，數字才不會兩邊對不上。

必算的：整體總數與每天平均、每週彙總（給趨勢圖）、每個重點頁面的指標、
表現最好的次要頁面。對比時兩期都算，並反推新增期間的排名。

## 第四步：交付，順序不能顛倒

一律 **先產 Markdown 分析檔，請使用者確認內容後，才產 HTML**。

| 檔案 | 放什麼 | 不放什麼 |
|---|---|---|
| `<客戶> GSC 成效分析_<起>_<迄>.md` | 資料範圍與限制、指標判讀、本期判讀、建議事項 | 大量表格 |
| `<客戶> GSC 成效報告_<起>_<迄>.html` | 圖表、數字卡、表格 | 判讀、建議、任何解釋性段落 |

**使用者只回答了視覺風格，不等於同意你開始做 HTML。** 要等他明確確認 MD 內容之後
才動手。MD 改過之後，HTML 也要跟著重出。

HTML 裡唯一允許的文字，是讀懂表格所必需的定義（例如「數字越小越前面」）。一句話
講完，不要延伸解釋。

**動手寫 HTML 之前一定要確認視覺風格。** 每個客戶專案不同，不要直接套預設色。
去客戶網站抓實際用色比憑感覺配準：
`curl -sL <網址> | grep -oE '#[0-9a-fA-F]{6}' | sort | uniq -c | sort -rn | head -25`
（要濾掉 WordPress／Gutenberg 預設調色盤 `#ff6900` `#fcb900` `#7bdcb5` `#8ed1fc`
`#9b51e0` `#f78da7` `#cf2e2e`）。換過配色後，回頭掃一次文案裡提到顏色的句子，以及
圖例色塊的 inline style —— 它們寫死在 HTML 裡，不吃 CSS 變數。

配色分工：綠 = 點擊／正向成長；藍 = 曝光；橙 = 警示、排名變差、需要注意。

## 一定要避開的判讀錯誤

- **平均排名是以曝光加權、跨所有查詢／日期／地區／裝置平均出來的**，不是「我們在
  關鍵字 X 的名次」。使用者說「我搜了我們是第 1」時要解釋這件事 —— 無痕視窗仍會
  依 IP／地區在地化。
- **排名數字越小越前面。** 每次呈現都要講一次，不然客戶會把「7.2 變 6.6」讀成退步。
- **排名變差但曝光暴增，通常是好事** —— 被更多長尾字帶出來，把加權平均拉高了。
  真正要警惕的是排名變大、曝光持平或下降、點擊也掉。
- **點閱率會被高曝光稀釋**，可能在其他都變好時反而下降。以點擊與曝光為主，把
  點閱率當成「標題／描述夠不夠吸引人」的獨立訊號。
- **高曝光 + 低點閱率 = 優化機會**，不是失敗。Google 已願意給排名，只是摘要沒贏得點擊。
- **排名很前面卻零點擊 = 搜尋意圖不符**，不是標題問題。這種字排名已無空間，
  要處理的是落地頁有沒有正面回應那個詞。
- **兩期天數不同就比每天平均，不要比原始總數。**
- **累積 vs 新增：** 較新的匯出常是從同一個起始日累積下來的。相減前先用日期 merge
  驗證重疊期間完全一致。用曝光加權恆等式反推新期間排名：
  `排名新 =（排名總×曝光總 − 排名舊×曝光舊）÷ 曝光新`。
- **排除不完整的最後一週／最後幾天。** GSC 最近 1–3 天常未統整完，畫上去像崩盤。

## 文章上線天數（做我方供稿分析時的必要校正）

**資料期間 92 天，不代表文章上線了 92 天。** 期間中才發布的文章，累計點擊與曝光
天生偏低，跟上線滿整段期間的頁面放在一起比是不公平的。

- 一律取得每篇的發布日期（頁面 JSON-LD 的 `datePublished` 通常抓得到：
  `curl -sL <網址> | grep -oE '"datePublished":"[^"]*"'`），算出**上線天數**與
  **每天點擊／每天曝光**，用每天平均當互比基準。
- 在報告裡明說：**點擊與曝光受上線天數影響、不可直接互比；點閱率與平均排名不受
  影響，是公平的比較基礎。**
- 上線未滿約 20 天的文章樣本過小，標註出來，不要據以判讀好壞。
- 要做同期化估計（用每日速率推到整段期間）可以，但要標明是粗估且偏保守 ——
  新文章通常需要數週才進入穩定排名。

## 我方供稿 vs 客戶自有頁面

當使用者提供了「我方寫的文章」清單，報告的主軸就是這條切分：

- 我方文章、客戶自有／他方供稿頁面、品牌官網頁，**三組分開統計**。品牌頁點閱率
  天生就高，混在一起排序會讓內容頁失真。
- 比較時以點閱率與平均排名為主（不受上線天數影響），累計量放參考。
- **站上最大的機會可能落在不是我方寫的頁面上。** 照實講，並把它寫成「建議由我方
  接手優化」的提案，這對客戶與對自己都是有價值的發現。
- 清單網址與 GSC 實際收錄路徑可能不同（改過路徑、有 canonical）。比對時用 slug
  而非完整網址，發現落差要在報告裡說明怎麼合併的。

## 驗證後才交付

HTML 用 headless Chromium（Playwright）實際 render 過再交：每個表格都有列、
無 JS 錯誤、圖表有畫出來、沒有殘留 placeholder、沒有漏網的長篇敘述、版面沒爆開。
檔名有中文或空白時用 `pathlib.Path(...).as_uri()` 產生 file URI。

圖表程式碼要包在 `typeof Chart === 'undefined'` 的保護判斷裡，並讓表格與清單在
圖表程式碼「之前」先渲染 —— 否則一次 CDN 載入失敗就會讓整份報告空白。

## 與另一份 skill 的分工

- **這份（API 版）** —— 環境有 `tools/gsc_fetch.py` 與憑證時用。第一步先確認目的。
- **「行銷」GSC 成效分析** —— 使用者直接丟 GSC 介面匯出的 CSV 時用。那份詳細記錄了
  介面匯出的檔案結構與陷阱（錨點網址被當獨立列、查詢截在 1,000 列、查詢與頁面無法
  對應），以及報告樣板 `assets/report_template.html` 的用法。需要時去讀。
