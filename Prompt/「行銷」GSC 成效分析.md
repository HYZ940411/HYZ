# GSC 成效報告

用 Google Search Console 匯出的 CSV，做出可直接交付客戶的報告。這份 skill
涵蓋兩種報告類型，而且同樣重要的是 —— 那些讓 GSC 資料很容易被解讀錯誤的地雷。

## 第一步：先確認目的，再開始算

**拿到檔案之後，先問使用者這次分析要幹嘛，不要直接開始算。** 手上有什麼資料決定了
「能做什麼」，但目的決定「該做什麼」—— 同一份匯出檔，為了交代成效、為了驗證策略、
為了找優化清單，要算的東西與報告長相完全不同。不先問就開算，會產出一份什麼都提到、
但什麼都不深的報告。

用選項式提問，一次問完。至少要確認：

1. **這次的目的是哪一種（可複選）** —— 見下表
2. **重點頁面清單** —— 我方供稿／正在合作的那批文章網址
3. **文章發布日期** —— 只要重點頁面裡有任何一篇是期間中才上線的，就必須拿到
4. **有沒有前期資料** —— 決定能不能做對比

| 目的 | KPI | 需要的資料 | 報告長相 |
|---|---|---|---|
| **1. 對客戶交代成效**（續約／請款） | 我方頁面的點擊、曝光、排名逐期變化 | 兩期匯出 | 成長百分比放最前面，「之前 → 之後」放底下；我方頁面與其他頁面分開列 |
| **2. 策略驗證**（假設對不對） | 目標大字的排名軌跡、字族的曝光廣度 | 兩期查詢檔；理想上要單頁查詢匯出 | 圍繞字族：排到第幾名、跟上期比前進多少、卡點在排名還是點擊 |
| **3. 找可執行的優化清單** | 預估可回收點擊數 | 單期即可 | 依「動手就能回收的量」排序，每條附現況數字與預估效益 |
| **4. 診斷異常**（流量掉了） | 掉最多的頁面與字 | 兩期，逐頁相減 | 先給結論（掉在哪、掉多少），再給排除法：索引狀態、改版、演算法更新 |
| **5. 選題與需求探勘** | 有曝光但我們沒有對應內容的字 | 單期查詢檔（注意被截在 1,000 列） | 依曝光排序的字群清單，標出目前由哪個頁面承接、或根本沒人承接 |

目的 1、2、4 需要兩期資料；3、5 單期就能做。**若使用者要的是 1 或 2，但只給了一份
匯出檔，要先講清楚做不了哪一段、需要補什麼檔案，再問要不要先做 3。不要硬湊一份
看起來像成長報告的東西。** 缺的資料要在 Markdown 的建議事項裡寫成具體的索取清單
（哪個頁面、哪個期間、在 GSC 介面怎麼匯出）。

**目的 2 特別容易被資料形狀卡住。** 三份匯出檔之間查詢與頁面無法對應，且查詢檔沒有
日期維度 —— 這代表「哪個字漲了、哪個字掉了」本質上答不出來。遇到這種情況，把「為什麼
答不出來、要補什麼才答得出來」寫進報告，並改用能做的：呈現目標字族的現況排名、
標出卡點在排名還是在點擊。

## 交付物是兩份檔案，而且有先後順序

一次交付 **Markdown 分析檔** 和 **HTML 數據報告** 兩份，分工清楚：

| 檔案 | 放什麼 | 不放什麼 |
|------|--------|----------|
| `<客戶> GSC 成效分析_<起>_<迄>.md` | 資料範圍與限制、指標判讀、本期判讀、建議事項 | 大量表格 |
| `<客戶> GSC 成效報告_<起>_<迄>.html` | 圖表、數字卡、表格 | 判讀、建議、任何解釋性段落 |

**一律先產 Markdown，請使用者確認內容後，才產 HTML。** 判讀和建議是最需要人來校準的
部分，先確認完再花力氣做版面，才不會白做。HTML 只是把已確認的數據視覺化。

**「確認」必須是使用者親口說 MD 內容沒問題、可以做 HTML，不能用其他訊號代替。**
產完 MD 之後如果還有子問題要問（例如某頁要不要納入重點清單、HTML 視覺風格要用什麼），
可以跟確認一起問，但使用者回答了那些子問題，不等於他確認了整份 MD 的判讀與數字。
在動手做 HTML 之前，必須明確再問一次「MD 內容確認沒問題了嗎，我要開始做 HTML」，
拿到肯定答覆才能繼續——沒問到就先做，就算後續每個子問題使用者都有回，也算違反這條。

HTML 裡唯一允許的文字，是讀懂表格所必需的定義（例如「曝光 ≥ 3,000 且點閱率 < 1.5%」、
「錨點已併回母頁面」、「數字越小越前面」）。一句話講完，不要延伸解釋 —— 那些屬於 MD。

## 什麼時候用哪一種報告

- **單一期間報告** —— 一個日期區間。整體指標、每週趨勢、每篇文章拆解、其他表現好
  的頁面。適合第一次看，或做一份獨立的快照。
- **期間對比成長報告** —— 兩個日期區間（例如「跟上次報告比成長了多少」）。這通常
  才是客戶要的。強調「變化」，把最重要的成長數字放到最前面。

如果使用者給了一份較新的匯出檔加上一個前期日期區間，預設就做**對比成長報告**。

**只有一份匯出檔（沒有前期資料可對照）時**，做單一期間報告，並額外用「期間內前後對半
切」做對比 —— 例如 92 天切成前 46 天 / 後 46 天。兩段天數相同，可直接比，不必換算日均。
要在 MD 裡講清楚這是期間內對比、不是跟上一期比。注意頁面檔和查詢檔沒有日期維度，
**只有圖表檔切得開**，所以頁面層級無法做前後對比，要照實說。

## GSC 匯出檔的格式（先讀這段）

一份標準的 GSC「成效」匯出，是一個壓縮檔／一組各自獨立的 CSV，每一份是**不同維度、
彼此之間沒有共用欄位**：

| 檔案（中／英）      | 欄位                             | 顆粒度            |
|---------------------|----------------------------------|-------------------|
| 查詢 / Queries      | 查詢字詞、點擊、曝光、點閱率、排名 | 每個搜尋字一列    |
| 網頁 / Pages        | 頁面網址、點擊、曝光、點閱率、排名 | 每個頁面一列      |
| 圖表 / Chart / Dates| 日期、點擊、曝光、點閱率、排名     | 每天一列          |

**最關鍵的限制 —— 查詢和頁面之間沒有對應關係。** 查詢檔「不會」告訴你某個關鍵字
是哪個頁面接到的，網頁檔也「不會」列出某個頁面排上了哪些關鍵字。任何「文章 X 排上
了哪些關鍵字」的答案，光靠這三個檔案都只是**用主題／類別去推測**，不是資料本身給
的事實。要拿到真正的對應，使用者必須在 GSC 介面裡，先用單一「頁面」做篩選，再切到
「查詢」分頁去看 —— 一個頁面匯出一次。被問到時就照實講，不要編造對應關係。

欄位標題可能是中文或英文，點閱率是像 `1.43%` 的字串。計算前要先正規化：
`df['ctr'] = df['點閱率'].str.rstrip('%').astype(float)`
（記得同時處理 `點閱率` 和 `CTR` 兩種欄名）。

**另外兩個一定要先處理的陷阱：**

- **網頁檔會把錨點網址（`頁面#章節`）當成獨立的一列。** 同一篇文章可能散成 7、8 列，
  而且錨點列通常是「高曝光、幾乎零點擊」。不併回去的話，頁面層級的曝光會被灌水、
  點閱率會被嚴重低估，網頁檔的曝光總和也會遠大於圖表檔（實例：235,574 vs 170,875）。
  先 `url.split('#')[0]` 合併，排名要用曝光加權合併，不能取平均。
  合併後值得單獨報一個數字：有多少曝光是掛在錨點上 —— 這本身就是個發現，代表 Google
  把文章的某個小節當成答案在呈現。
- **查詢檔被 GSC 截在 1,000 列。** 這常常只涵蓋全站點擊的一半（實例：47.3%）。一定要
  算出涵蓋率（`查詢檔點擊總和 ÷ 圖表檔點擊總和`）並在報告裡揭露，而且所有「品牌字佔
  幾成」之類的比例都要標明是「這 1,000 個字之內」的比例，不是全站比例。

## 指標怎麼解讀（避開這些坑）

把數字讀對，比視覺好看更重要。其中「排名」這個指標最會害人。

- **平均排名是「以曝光加權」而且「跨所有查詢、日期、地區、裝置」平均出來的。**
  它不是「我們在關鍵字 X 的名次」。一個頁面可以在使用者最在意的那個字排第 1，
  平均排名卻顯示 6，因為還有幾十個排在後面的其他查詢一起被平均進去。當使用者說
  「可是我搜了，我們是第 1 名」，就要解釋這件事 —— 而且無痕視窗仍會依 IP／地區
  做在地化，所以他看到的在地結果 ≠ 全站平均。
- **排名數字越小越好。** 每次呈現都要講一次；不然客戶會把「7.2 變 6.6」讀成退步。
- **排名「變差」但曝光暴增，通常是好事。** 當一個頁面開始被「更多」關鍵字帶出來，
  這些新字往往是排名較後面的長尾查詢，把加權平均拉高了。這是覆蓋範圍變廣，不是
  在衰退。判斷訊號：排名變大 + 曝光變大同時發生。真正要警惕的是相反的組合 ——
  排名變大、曝光卻持平或下降、點擊也掉，這才是真的走弱。
- **點閱率可能在其他都變好的時候反而下降。** 曝光大幅上升會稀釋點閱率，即使原始
  點擊數是增加的。呈現時以點擊和曝光為主，把點閱率當成「標題／描述夠不夠吸引人」
  的獨立訊號來看。
- **高曝光 + 低點閱率 = 標題／描述的優化機會**，不是失敗。這種頁面是最快的成效
  來源：Google 已經願意給排名，只是那段摘要沒能贏得點擊。

## 兩個期間怎麼正確比較

「累積 vs 新增」這個問題，每一次對比都會踩到：

- **較新的 GSC 匯出檔，常常是從同一個起始日「累積」下來的**，不是只有新的那段。
  相減之前，先檢查新檔的前段日期是否等於舊檔的日期。如果一致，代表新檔 = 舊期間
  + 新期間，所以新增期間 = `新檔總計 − 舊期間`（在圖表檔可以逐日相減，在網頁檔
  可以用「新網頁值 − 舊網頁值」逐頁相減）。
- **相減前先驗證重疊期間完全一致。** 用日期 merge，確認共同天數的點擊／曝光相同。
- **當兩段期間天數不同，比「每天平均」，不要比原始總數** —— 46 天 vs 29 天用總數
  比不公平。各自算出點擊／天、曝光／天，再用日均去算成長。
- **用曝光加權的恆等式反推新期間的排名**：
  `排名總 × 曝光總 = 排名舊 × 曝光舊 + 排名新 × 曝光新`，
  所以 `排名新 =（排名總×曝光總 − 排名舊×曝光舊）÷ 曝光新`。注意：累積匯出檔裡
  一個頁面顯示的排名，仍然把舊期間混在裡面，所以直接拿原始檔的「現在排名」會低估
  近期的變化 —— 當故事是關於新期間時，要把新增期間的排名反推出來。
- **圖表要排除不完整的最後一週／最後幾天。** GSC 最近的 1～3 天常常還沒統整完；
  一個只計到一半的最後一週，看起來會像崩盤。把它從趨勢裡拿掉，並簡短說明一次原因
  —— 不要畫上去然後再道歉。

## 重點頁面

報告通常圍繞使用者指定的一份頁面清單（正在合作的那批文章）。永遠把這些放在最前面、
依點擊排序，其餘當次要。追蹤每個重點頁面的真實標題 —— 需要的話去抓（一個頁面常會連到
它的姊妹文章，所以抓一次可能就能看到好幾篇的標題）—— 並在報告裡把標題連到網址。

**使用者沒給清單時，不要停下來等。** 先依實際點擊取前 10～12 名當內容頁，照常把分析
做完，並在 Markdown 的「資料範圍與限制」明確寫出這是預設排序、若合作標的是另一批文章
需要另行提供網址。反正 MD 本來就要給使用者確認，這個問題會在那一關一併解決。

把品牌／官網頁（首頁、關於我們、產品、通路、公告）跟內容頁分開列。品牌頁的點閱率
天生就高（實例：首頁 14.65% vs 全站 1.95%），混在一起排序會讓內容頁的表現失真。

## 建置流程

1. **先讀這份 skill，再檢視檔案。** 對每個 CSV 做 `head`，判斷標題語言，找出日期
   範圍（圖表檔的 min／max）、列數。確認哪個檔對應查詢／網頁／日期。
2. **先確認目的**（見「第一步：先確認目的」），連同重點網址清單、文章發布日期、
   有無前期資料一次問完。目的決定後面要算什麼、報告怎麼組織。**確認前不要開始算。**
3. **確認範圍與風格。** 單一期間還是對比？如果是對比，前期日期區間是什麼？用
   「檢查重疊」來解決「累積 vs 新增」的問題。**同時確認這個專案要用什麼視覺風格**
   —— 見「文案與設計慣例」，不要預設套用預設色。
4. **用 Python（pandas）計算。** 整體總數 + 每天平均；每週彙總給趨勢圖；每個重點
   頁面的指標（對比時算兩期，並反推新增期間的排名）；表現最好的次要頁面。把結果
   輸出成一份 JSON，後面兩份交付物都從這份 JSON 產，數字才不會兩邊對不上。
   沒有 pandas 也不要卡住 —— 這種資料量用標準函式庫的 `csv` 就夠了。
5. **抓真實標題**（重點頁面，以及值得一提的次要頁面）。
6. **先產 Markdown 分析檔，交給使用者確認。** 判讀、資料限制、建議事項都寫在這裡。
   在這一步就把所有假設攤開講（做了哪種報告、重點頁面清單怎麼來的、哪些是推測），
   等使用者確認或修正。**確認前不要動 HTML。** 過程中若還有子問題要問（重點頁面清單、
   視覺風格等），可以跟確認一起問，但那些子問題的答覆不算數——一定要明確問到
   「MD 可以了嗎，我要開始做 HTML」，拿到使用者親口的肯定答覆才算數。
7. **拿到明確的肯定答覆後才渲染 HTML。** 注入同一份 JSON。只放圖表、數字卡、表格。
8. **實際 render 出來驗證** 再交付：用 headless Chromium（Playwright）確認每個
   表格都有填、無 JS 錯誤、圖表有畫出來、不完整期間確實被排除、沒有殘留的舊配色，
   而且沒有漏網的長篇敘述。見「渲染與驗證」。
9. **交付兩份檔案**，說明哪份是給客戶看的、哪份是內部判讀。只有被要求時才提供 PDF。

## 文案與設計慣例

- **語氣是專業書面語，不是口語。** 對象是客戶沒錯，但「平實」不等於閒聊。這些寫法
  一律不要：「先講一件很重要的事」「不過也別過度緊張」「這個組合要正視」「我們把…」
  以及任何安慰、鋪陳、自問自答的句子。直接陳述事實與推論即可。用詞照 GSC 原本的
  「曝光」「點擊」「點閱率」「平均排名」，不要換成「被看到」「被點擊」這類代換 ——
  客戶看的是自己的 GSC，術語一致才對得起來。
- **對比報告從成長開始講。** 大大的百分比放最上面，「之前 → 之後」放底下。讓人五秒
  內就看懂這個亮點。
- **不要從三檔匯出去編造某頁的關鍵字清單。** 被問到某頁排上哪些關鍵字，就給「用主題
  推測」的版本，並明講這是推測、以及怎麼拿到真正的資料（在 GSC 用單頁篩選）。
- **格式：** 極簡。HTML 用表格與圖表承載資訊，不要用散文；MD 用短段落加分層標題，
  結論寫在段首。只有在圖表／表格真的有幫助時才放。
- **動手寫 HTML 之前，一定要先跟使用者確認視覺風格。** 每個客戶專案的品牌風格都不同，
  不要直接套下面那組預設色就開始做。資料計算的部分可以照常先跑完，但在選配色、寫樣式
  之前停下來問 —— 用選項式的提問（沿用該客戶既有品牌色／沿用上次同客戶報告的風格／
  下面的預設風格）會比開放式提問快。
- **拿到風格方向後，去客戶網站抓實際用色**，比自己憑感覺配準得多：
  `curl -sL <網址> | grep -oE '#[0-9a-fA-F]{6}' | sort | uniq -c | sort -rn | head -25`
  出現次數最高的通常就是品牌色。要濾掉 WordPress／Gutenberg 的預設調色盤
  （`#ff6900` `#fcb900` `#7bdcb5` `#8ed1fc` `#9b51e0` `#f78da7` `#cf2e2e` 等）。
- **換配色之後，一定要回頭掃一次文案裡提到顏色的句子。** 「灰色是前期、綠色是本期」
  這種說明會在換色後直接變成錯的。連圖例色塊的 inline style 也要一起換 —— 它們寫死在
  HTML 裡，不吃 CSS 變數，很容易漏掉。
- **預設視覺風格**（只在使用者說「照預設就好」時才用）：白底，橄欖／工裝綠為主色
  （`#4f6b3a` / 深 `#34492a` / 淺 `#e6ebde`），搭配藍色（`#3a6ea5`）與橙色
  （`#c1622f`）當點綴，讓各項指標一眼就能區分。字體：Noto Sans TC（從 Google Fonts
  載入以正確顯示中文）。基礎字級大一點（約 17px）對非技術背景的對象比較好讀。
- **好用的點綴色分工：** 綠 = 點擊／正向成長／品牌；藍 = 曝光；橙 = 警示、排名變差、
  以及「需要注意」的地方。

## 渲染與驗證

樣板從 CDN 載入 Chart.js。在沙箱環境 CDN 可能被擋，所以**把所有圖表程式碼包在
`typeof Chart === 'undefined'` 的保護判斷裡**，並且讓資料驅動的內容（表格、清單）
在圖表程式碼「之前」先渲染 —— 否則一次 CDN 載入失敗就會讓整份報告空白。樣板已經
這樣做了，請保留。

交付前用 Playwright 驗證：

```python
from playwright.sync_api import sync_playwright
import pathlib
errs = []
with sync_playwright() as p:
    b = p.chromium.launch(); pg = b.new_page()
    pg.on('pageerror', lambda e: errs.append(str(e)))
    pg.goto(pathlib.Path('/path/report.html').as_uri(), wait_until='networkidle', timeout=45000)
    pg.wait_for_timeout(3000)
    # 每個表格都有列？（0 代表該表沒填到）
    print(pg.evaluate("[...document.querySelectorAll('table')].map(t=>t.querySelectorAll('tbody tr').length).join(',')"))
    # 圖表真的畫出來了？
    print(pg.evaluate("[...document.querySelectorAll('canvas')].every(c=>c.width>0)"))
    # 還有沒有殘留的 placeholder？
    print(pg.evaluate("/__[A-Z_]+__/.test(document.body.innerText)"))
    # 有沒有漏網的長篇敘述？（HTML 應該只有數據）
    print(pg.evaluate("""[...document.querySelectorAll('main p, main div')]
        .filter(e=>e.children.length===0 && e.innerText.trim().length>40)
        .map(e=>e.innerText.trim().slice(0,60))"""))
    # 版面有沒有爆開？
    print(pg.evaluate("document.documentElement.scrollWidth > window.innerWidth"))
    b.close()
print("JS errors:", errs or "none")
```

檔名有中文或空白時，用 `pathlib.Path(...).as_uri()` 產生 file URI，不要自己拼
`file://` 字串。換過配色的話，另外用 `grep` 掃一次舊色碼確認沒有殘留。

要出 PDF 時（只有被要求才做），用 Playwright 的 `page.pdf(...)` 把同一份檔案以 A4、
`print_background=True` 輸出 —— 它保留字體、顏色、圖表的效果遠比 wkhtmltopdf 好。
